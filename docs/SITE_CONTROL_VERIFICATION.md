# Exact-host HTTPS file control

This extends M4. Public research, report saving and owner-provided analysis still work without site proof. A proof establishes control of one HTTPS file at one time. It does not establish legal ownership, validate business facts, authorize edits, connect Shopify or grant outreach consent. Existing report JSON, citations and ownership flags remain immutable.

## Merchant flow

Open **Business → Verify a website you control**. A currently verified workspace owner or admin enters an exact host and creates a challenge. Creation and page reads make no website requests. Publish the generated line as uncompressed `text/plain` at the displayed exact URL, without authentication or redirects:

```text
https://<exact-host>/.well-known/ayo-site-verification.txt
```

Explicitly submit **Check verification file**. A match becomes a seven-day proof. The challenge expires after one hour; successful, expired and revoked challenges expose no text. Cleanup removes expired encrypted material while retaining history. Renewal requires a fresh challenge; replay cannot extend a verified proof. Revocation applies to every proof and pending challenge for that workspace/host, including an older proof while renewal is pending. It does not edit the external site. www, apex and subdomains require separate proofs.

## Exact operation and limits

One check issues at most these GETs:

1. `https://<exact-host>/robots.txt` — at most 64 KiB.
2. The fixed verification-file URL — at most 4 KiB, only if robots permits access.

No redirects, sitemap/discovery requests, rendering, paid crawler or model calls. Existing public-IP-pinned DNS/TLS transport validates destinations. Robots refusal, unavailable/redirected/non-text policy, private DNS, wrong body, HTML, oversized responses and compressed files fail safely. Missing robots (404/410) permits the fixed file request. Pacing up to five seconds is honored; longer pacing fails. One 15-second deadline covers both requests. A single CRLF or LF after the exact line is allowed; other text/whitespace does not match.

Maximum provider usage per check: **Gemini 0, Firecrawl 0, mail 0, provider charge USD 0**. Normal hosting operation is not new spending authorization. No credit purchases/billing changes. Limits: five checks/challenge, at least 60 seconds between workspace/host checks, 20 checks/actor/hour, three new challenges/workspace/hour and ten/actor/day. Committed hashed 45-second leases fence concurrent, interrupted and superseded results. Serialized creation reuses an active pending challenge.

## Data and access

Random challenge material is encrypted at rest; only verified owners/admins may view pending instructions or mutate proofs. Members read only their workspace’s status/history. Opaque IDs are workspace-scoped; commands require CSRF and a current authenticated session. Account, membership, role, lease and expiry are rechecked after I/O. Session revocation, actor demotion or challenge revocation during I/O prevents publication. No database lock spans retrieval.

Stored metadata includes host, method, timestamps, lifetime, attempts and successful response SHA-256. Audits retain the fixed source URL, successful hash and outcome, without challenge text, failed bodies or arbitrary upstream errors. No text is sent to Gemini. Account removal deletes exclusive-workspace proofs; departing accounts’ pending shared challenges are revoked and attribution removed. Verified shared history remains with the workspace.
